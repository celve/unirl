---
title: Extending UniRL
description: Where to add models, rollout engines, train-side algorithms, rewards, training backends, and recipes.
---

Use existing boundaries rather than adding cross-cutting glue. Most extensions need one implementation package, one registered config, one recipe, and one focused test or compose check.

## Extension Map

| Goal | Primary location | Required config |
|---|---|---|
| Add a model | `unirl/models/<model_name>/` | `@register_config(group="model", name="<model_name>", target=...)` |
| Add a rollout engine | `unirl/rollout/engine/<engine>/` | `@register_config(group="rollout/engine", name="<engine>", target=...)` |
| Add a train-side algorithm | `unirl/algorithms/` | a `BaseAlgorithmConfig` subclass via `@register_config`, bound under a track's `algorithm:` node |
| Add a reward scorer | `unirl/reward/local/` | `@register_config(group="reward/component", name=..., target=...)` |
| Add a training backend | `unirl/train/backend/` | the `Remote` backend contract (alongside `FSDPBackend`) |
| Add a recipe | `recipes/<bucket>/<recipe>.yaml` | `--config-name=<bucket>/<recipe>` |

## Adding a Model

1. Add `unirl/models/<model_name>/`.
2. Register the model config in the `model` group.
3. Implement a bundle that exposes the trainable stages needed by training and rollout.
4. Add condition, text/vision, diffusion, and VAE helpers as needed.
5. Add at least one `recipes/<bucket>/<recipe>.yaml` recipe.
6. Document required external checkpoints through YAML env interpolation or launcher docs.

## Adding a Rollout Engine

1. Add a typed config under `unirl/rollout/engine/<engine>/`.
2. Register it in group `rollout/engine`.
3. Implement the engine contract from `unirl/rollout/engine/base.py`.
4. Return canonical `RolloutResp` data (populate `tracks[name]`).
5. If the engine is dedicated, define trainer-to-rollout weight sync.

## Adding a Train-Side Algorithm

The training loss is a per-track `StageAlgorithm`. Add a new class only when the loss math changes (recipe compositions like DanceGRPO / MixGRPO reuse `DiffusionGRPO`).

1. Subclass `StageAlgorithm` (`unirl/algorithms/base.py`).
2. Define a config subclassing `BaseAlgorithmConfig` and register it with `@register_config`.
3. Implement `compute_loss_and_backward(...)` — replay the stage, compute the loss, call `backward()`.
4. Set `supports_multi_update` to match whether the loss is valid across multiple optimizer steps on one rollout shard, and `requires_ema_rollout` only for off-policy losses that need EMA sampling (NFT).
5. Bind the class under the track's `algorithm:` node in a recipe.

See the generated [Algorithms Package README](/en/docs/architecture/readme-reference/unirl-algorithms) for the full contract.

## Adding a Reward Scorer

Add the spec and scorer near the reward implementation under `unirl/reward/local/`. Prefer `LocalRewardBackend` for in-process model scorers because it provides device resolution, eager load, `offload()`, and `onload()`. Register the spec with `@register_config(group="reward/component", ...)`. For out-of-process scoring, point the reward backend at the remote service. See [Rewards](/en/docs/guides/rewards).

## Training Backends and Parallelism

New **training-backend** or **parallelism** work (a new FSDP / SP / EP plan, or a VeOmni-style backend) targets the backend contract under `unirl/train/backend/`: implement the same `Remote` surface as `FSDPBackend` and map `TrainTopology` onto a parallel plan rather than hardcoding shard sizes. See [Trainer & Training Stack](/en/docs/architecture/trainer-v2) and the generated [Train Stack README](/en/docs/architecture/readme-reference/unirl-train).

## Agent Tip

When an agent is asked to implement a new feature, first map the request to the table above, then read the closest package README before editing code.
